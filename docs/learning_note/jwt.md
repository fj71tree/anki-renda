# JWT (JSON Web Token)

## 構造

JWTは `.` で区切られた3つのパーツで構成される。

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOjEsImV4cCI6MTcwMH0.abc123xyz
ヘッダー (Base64URL)                  ペイロード (Base64URL)           署名
```

各パーツはJSONをBase64URLエンコードしたものであり、暗号化ではない。トークンにアクセスできる人なら誰でも中身を読める。

### ヘッダー

```json
{ "alg": "HS256", "typ": "JWT" }
```

使用するアルゴリズムが含まれる。サーバー側はこれを読んで検証に使う。

### ペイロード

```json
{ "userId": 5, "exp": 1700000000 }
```

ユーザーIDや有効期限など識別情報が含まれる。機密情報（パスワードなど）は入れてはいけない。

### 署名

```
HMAC_SHA256(Base64URL(ヘッダー) + "." + Base64URL(ペイロード), secret)
```

ヘッダーとペイロードを連結した文字列を、secretを使ってHMAC-SHA256で計算した値。

## 署名の仕組み

### 署名の流れ

```
1. ログイン
   フロントエンド→サーバーに認証情報を送る。

2. トークン生成
   サーバーが認証情報を確認し、ペイロードに値を入れて署名
   → access token と refresh token を生成

3. トークンをフロントエンドに返す

4. APIリクエスト
   フロントエンド → サーバー
   サーバーが署名と期限を検証 → 問題なければレスポンスを返す

5. もし、access token が期限切れの場合
   サーバー → フロントエンドに 401 Unauthorized を返す

6. トークンのリフレッシュ
   フロントエンド → サーバー
   401をフロントエンドが検知した場合、 refresh tokenをサーバーに送る
   サーバーが refresh token を検証 → 新しい access token を発行し、レスポンス

7. リクエストをリトライ
   フロントエンドが新しい access token で 4 をやり直す
```

### HMACとは

SHA256は任意の文字列を固定長の値に変換するハッシュ関数。

```
SHA256("hello") → "2cf24dba..."  # 常に同じ値になる
```

ただしSHA256だけでは誰でも計算できてしまう。HMACは秘密鍵を混ぜてハッシュ計算する仕組みで、secretを知らないと同じ値を計算できない。

```
HMAC_SHA256("hello", "mysecret") → secretを知る人だけが計算できる値
```

### 改ざん検知

攻撃者がペイロードを書き換えようとしても、secretを知らないため正しい署名を作れない。

```
元のトークン:
  ペイロード: { "userId": 5, "exp": 1700000000 }
  署名: "abc123"

攻撃者が改ざん:
  ペイロード: { "userId": 1, "exp": 1700000000 }  ← 他人のIDに書き換え
  署名: "abc123" のまま（secretを知らないので作れない）

サーバーの検証:
  攻撃者から受け取ったヘッダー+ペイロードで署名を再計算 → "xyz789"
  "xyz789" ≠ "abc123"  → 弾く
```

## access token 漏洩対策

JWTはコピーしてそのまま送ることができるため、access token が漏洩すると攻撃者に不正アクセスされてしまう。これは有効期限（`exp`）で対策している。

```
ログイン（10:00）  → ペイロード: { "userId": 5, "exp": 10:05 }
APIリクエスト（10:06）→ サーバーが exp を確認 → 期限切れで弾く
```

ペイロードの `exp` が違えば同じsecretでも署名は変わるため、ログインするたびに異なるトークンが発行される。
secretが漏洩していなければ、攻撃者は新しい署名を推測することはできない。

### access token と refresh token

```
access token:  有効期限を短く（5〜15分）
                → 盗まれても短時間で無効
refresh token: 有効期限を長く（数日〜数週間）
                → DBに保存して管理、ログアウトで無効化できる
```

## JWTのメリット

ペイロードの中身はサーバーが署名で保証しているため信頼できる。サーバーはDBを見ずにペイロードのuserIdを信頼できるため、セッション情報をサーバー側で保持しないステートレスな認証が実現できる。

```
セッション認証: リクエストのたびにDBでセッションを検索する
JWT認証:       secretで署名を検証するだけ（DBアクセス不要）
```

## 注意点

### secretの管理

secretが漏れると、攻撃者が任意のペイロードで正規の署名を作れてしまう。コードにハードコードせず環境変数で管理する。

### トークンの盗難

JWTは「トークンを持っている人を信頼する」設計のため、トークンを盗まれないようにする必要がある。

対策：

- HTTPSで通信する（盗聴防止）
- localStorageのXSSリスクを意識する
- access tokenの有効期限を短くする
- ログアウト時にサーバー側でrefresh tokenを無効化する
