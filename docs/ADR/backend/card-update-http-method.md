# カード更新APIのHTTPメソッドについて

## 実現したいこと

- カードのチェック状態を変更できるAPIを作成したい
- REST APIの設計として自然なAPIにしたい
- なるべくシンプルなコードにしたい

## このADRで決めること

カードを更新するAPIで使用するHTTPメソッドを決める。

## 背景

カードのチェック機能を追加するにあたり、カード更新APIの見直しを行う。カードは以下の項目を持つ。

- 問題（question）
- 答え（answer）
- チェック状態（is_checked）

これまでは問題・答えの更新にPUTを使用していた。チェック機能を実装すると、以下のように操作によって更新する項目が異なる。

- カードを編集するときは、`question` と `answer` を更新
- チェック操作では、`is_checked` を更新

PUTはリソース全体の更新を表すため、PUTを使用する場合は、更新可能なカードの状態を一式送信する設計が自然である。これはチェック状態を変更したいときも問題と答えを送ることになる。既存のままPUTで統一するか、PATCHで統一するか、または更新する項目によってPUTとPATCHを使い分けるか検討を行う。

## 案の比較

### 比較軸

- フロントエンドの実装が複雑にならないか
- バックエンドの実装が複雑にならないか
- HTTPメソッドの用途として自然か

### 案1：PUTでカード全体を更新する

カードの更新にはPUTを使用し、更新可能な項目を一式送信する。例えばチェック状態のみを変更する場合でも、以下のようにカード全体を送信する。

```json
{
  "question": "apple",
  "answer": "りんご",
  "is_checked": true
}
```

**メリット**

- 既存のPUT方式をそのまま活用できる
- 更新時に送信する項目を統一できる

**デメリット**

- 1項目だけ変更する場合でも、変更しない項目を含めて送信する必要がある
- チェック状態だけを変更する場合でも、フロントエンドが `question` や `answer` の現在値を送信する必要がある

### 案2：PATCHで変更する項目のみ更新する

カードの更新にはPATCHを使用し、変更する項目のみを送信する。問題と答えを編集する場合は以下のように送信する。

```json
{
  "question": "apple",
  "answer": "りんご"
}
```

チェック状態のみを変更する場合は以下のように送信する。

```json
{
  "is_checked": true
}
```

**メリット**

- 実際に変更する項目だけを送信できる
- フロントエンドは変更対象の項目だけを意識すればよい
- 問題・答えの編集とチェック状態の変更を同じ更新方法で扱える
- DRFの部分更新の仕組みをそのまま利用できる

**デメリット**

- 複数の項目を部分更新できるため、更新可能な項目の組み合わせに制約が必要になった場合は、追加のバリデーションが必要になる

### 案3：問題・答えはPUT、チェック状態はPATCHで更新する

問題・答えの編集には既存のPUTを使用し、チェック状態の変更にはPATCHを使用する。問題と答えを編集する場合は以下のように送信する。

```json
{
  "question": "apple",
  "answer": "りんご"
}
```

チェック状態のみを変更する場合は以下のように送信する。

```json
{
  "is_checked": true
}
```

**メリット**

- 既存の問題・答えの更新処理をそのまま活用できる
- チェック状態の変更では `is_checked` のみを送信できる
- 操作ごとに更新対象を明確に分けられる

**デメリット**

- 同じカードの更新でありながら、更新する項目によってHTTPメソッドを使い分ける必要がある
- PUTとPATCHで更新対象を分けるため、Serializerを分ける、またはSerializerの設定を調整するなどの追加実装が必要になる
- カード更新APIの仕様が案2と比較して複雑になる

## 採用する案

案2を採用する。

カードの更新はPATCHに統一し、問題・答えの編集とチェック状態の変更を同じカード更新APIで扱う。また、PUTによる更新は使用しない。

## 理由

カードでは、問題・答えの編集とチェック状態の変更で更新する項目が異なる。特にチェック状態の変更では `is_checked` のみを変更すればよく、変更しない `question` や `answer` まで毎回送信する必要性はない。
案3のように、問題・答えの更新にはPUT、チェック状態の更新にはPATCHを使用する方法も実現可能である。しかし、PUTとPATCHで更新対象を分けるためにSerializerを分けるなど、バックエンド側に追加の実装が必要になる。
PATCHに統一することで、フロントエンドは実際に変更する項目だけを送信できる。また、DRFが提供する部分更新の仕組みを利用して、`question`、`answer`、`is_checked` を同じ更新APIで扱える。

以上から、カードの各項目の更新を同じPATCH APIで扱うことで、APIの仕様とフロントエンド・バックエンド双方の実装をシンプルに保つ。
